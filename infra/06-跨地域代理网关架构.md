## 1. 当前基线

当前集群只有两个跨地域节点：

- `gz`：广州，`k3s server`
- `sg`：新加坡，`k3s agent`

当前代理链路已经落地，实际形态是：

- `gz` 对公网提供代理入口
- `gz -> sg` 的节点间 relay 复用 `Kilo/WireGuard`
- `sg` 作为统一出公网出口
- 订阅文件由本地私密 YAML 渲染后，通过集群内静态 HTTP 服务分发

当前已上线协议：

- `HTTP CONNECT`
- `SOCKS5`
- `Shadowsocks`

## 2. 当前实际拓扑

```text
Client
  ->
gz public entry
  - 11080 SOCKS5
  - 11081 HTTP CONNECT
  - 18388 Shadowsocks
  - 11800 subscription
  ->
edge-ingress-gateway on gz
  - gost
  - hostNetwork
  - only forwards to sg Kilo IP
  ->
Kilo / WireGuard relay
  - 10.4.0.1 <-> 10.4.0.2
  ->
edge-egress-gateway on sg
  - sing-box
  - hostNetwork
  - only listens on 10.4.0.2
  ->
sg public egress
  ->
Internet
```

## 3. 当前组件与职责

### 3.1 广州入口

组件：

- `edge-ingress-gateway` DaemonSet

当前职责：

- 在 `gz` 宿主机公网监听代理端口
- 不在广州节点终止代理协议
- 只做 TCP/UDP 端口转发
- 上游固定转发到 `sg` 的 Kilo IP

当前实现：

- 引擎：`gost`
- 运行方式：`hostNetwork`
- 调度位置：`edge.role=ingress`

### 3.2 新加坡出口

组件：

- `edge-egress-gateway` DaemonSet

当前职责：

- 承接来自广州 relay 的代理协议
- 建立最终外连
- 统一从 `sg` 出公网

当前实现：

- 引擎：`sing-box`
- 运行方式：`hostNetwork`
- 调度位置：`edge.role=egress`
- 监听地址：只绑定 `10.4.0.2`

### 3.3 订阅分发

组件：

- `edge-subscription-server` DaemonSet
- `edge-subscription-files` ConfigMap

当前职责：

- 分发静态订阅文件
- 不承担控制面逻辑
- 不负责用户管理

当前实现：

- 运行在 `gz`
- `busybox httpd`
- `hostNetwork`
- 端口：`11800/tcp`

### 3.4 配置渲染

当前没有集群内长期运行的 `renderer/controller`。

实际 source-of-truth 是：

- 本地私密文件：`infra/.secrets/edge-gateway-values.yaml`

由本地脚本生成：

- `edge-egress-config` Secret
- `edge-subscription-files` ConfigMap
- `monitoring/edge-gateway-probe-config` Secret
- `SUBSCRIPTIONS.local.md`

因此，当前是：

- **本地渲染**
- **集群内静态运行**

而不是：

- 集群内动态控制面

## 4. 当前端口与绑定关系

| 协议/用途 | 广州入口 | 新加坡监听 | 说明 |
|---|---:|---:|---|
| SOCKS5 | `11080` | `10.4.0.2:11080` | `TCP + UDP` |
| HTTP CONNECT | `11081` | `10.4.0.2:11081` | `TCP` |
| Shadowsocks | `18388` | `10.4.0.2:18388` | `TCP + UDP` |
| 订阅服务 | `11800` | `gz:11800` | 静态 HTTP |

当前已知复用方：

- 终端/客户端显式代理
- `gz` 宿主机上的 `k3s/containerd` 镜像拉取（通过本机 `127.0.0.1:11081` 复用 `sg` 出口）

边界说明：

- `sg` 当前不需要对公网开放代理协议端口
- `sg` 上的代理服务只监听 Kilo 地址 `10.4.0.2`
- 代理 north-south 暴露只发生在 `gz`

## 6. 当前订阅模型

当前订阅输出包括：

- `Clash/Mihomo`
- `sing-box`
- `Shadowrocket`
- 通用 `HTTP/SOCKS` 手工连接信息

当前现实边界要特别说明：

- `Shadowrocket` 自动订阅当前只稳定使用单 `Shadowsocks` 节点
- 混合 `HTTP CONNECT / SOCKS5 / SS` 的 Shadowrocket 节点订阅格式，当前不作为受支持能力
- 因此当前各客户端里，真正最稳定的“统一订阅”仍然是基于 `SS`

## 9. 当前明确未做项

下面这些能力当前明确不做，原因也一并记录，避免以后从旧草案反推出现误判。

### 9.1 `Trojan / VLESS / Hysteria2 / TUIC / WireGuard` 客户端接入

当前不做的原因：

- 当前 `HTTP CONNECT / SOCKS5 / Shadowsocks` 已经能满足现有接入需求
- 新协议会显著增加：
  - 证书与传输层管理复杂度
  - 端口与模板维护成本
  - 监控与排障成本
- 对当前实际收益不明显，尤其在 `SS` 仍可用的前提下

### 9.2 透明代理 / TUN / 全局接管

当前不做的原因：

- 当前主要使用场景是显式代理入口
- 透明代理会引入：
  - `nftables/iptables`
  - `ip rule`
  - DNS 劫持
  - 回程与绕行规则
- 对当前 homelab 收益不如复杂度增长明显

### 9.3 用户系统 / 配额 / 限速 / 封禁

当前不做的原因：

- 当前是自用 homelab，不存在多租户运营需求
- Secret + 本地 YAML 已足够管理现有凭据
- 控制面复杂度与当前规模不匹配

### 9.4 多入口 / 多出口高可用

当前不做的原因：

- 当前只有 `gz` 和 `sg` 两个核心节点
- 引入多入口/多出口池后，发布、摘除、健康切换和灰度都会显著复杂化
- 当前阶段更重要的是把单链路保持稳定与可观测

## 10. 当前架构的现实判断

当前代理网关已经不是“计划中”，而是已经落地并在线运行的最小版本：

- 广州入口已经在线
- 新加坡出口已经在线
- 订阅服务已经在线
- 代理链路监控已经在线

但它仍然是一个 **最小可用版本**，而不是成熟平台：

- 只覆盖 `HTTP CONNECT / SOCKS5 / Shadowsocks`
- 仍然依赖本地脚本渲染配置
- 仍然是单广州入口、单新加坡出口
- 仍然复用 `Kilo/WireGuard` 作为 `gz -> sg` relay underlay

## 11. 后续修改方向

后续如果继续演进，建议只保留以下几个方向，不再把主文档写成长篇 phase 设计稿：

1. 引入 `nuc`，继续沿用当前 `Kilo/WireGuard` pseudo-underlay 模式扩展
2. 持续收敛公网暴露面，保持 `sg` 代理协议端口不对公网开放
3. 在明确收益成立之前，不急着补更多客户端协议
4. 如果未来节点级业务明显增多，再评估是否把通用 node mesh WG 从 Kilo 中独立出来
