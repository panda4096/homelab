# 06-跨地域代理网关架构（广州入口 / 新加坡出口 / Kilo 承载）

本文档定义一套运行在现有 `k3s + Kilo` 集群上的 **跨地域代理网关平台**。目标不是做单一 `TCP relay`，而是做一套可持续扩展、可观测、可发布、可订阅分发的 **自用** 代理体系。

> 范围：通用网络与平台工程设计。  
> 不承诺“支持所有历史协议的所有变种”，v1 以 **主流协议族全覆盖 + 轻量配置源** 为目标。

---

## 1. 当前基线

### 1.1 已经具备

- 双节点集群：
  - `gz`：广州，`k3s server`
  - `sg`：新加坡，`k3s agent`
- Kilo 已正常建立跨地域 WireGuard mesh
- `kilo.squat.ai/force-endpoint` 已显式配置
- `ingress-nginx` 已采用 `DaemonSet + hostNetwork` 运行
- 基础监控、网络探测、WireGuard/Kilo 指标已上线

### 1.2 已确认的现实约束

- 当前只有 `1` 个广州入口节点和 `1` 个新加坡出口节点
- 当前 `80/443` 已由 `ingress-nginx` 占用，不适合再给代理数据面抢占
- 当前尚未建立：
  - `edge.role` / `edge.location` 标签体系
  - 代理专用 namespace
  - 认证、配额、订阅分发、用户管理
  - UDP/QUIC 数据面
  - 多出口池、故障摘除、灰度发布
- 2026-04-04 已清理广州宿主机上的残留 `clash` 进程；当前集群内无 `clash` Service

### 1.3 结论

现有基础设施 **足以开始实施平台代理 v1**，但只能先交付：

- 单广州入口
- 单新加坡出口
- 单集群内编排
- 可滚动升级但不是真正高可用

如果目标是对标成熟中转服务商，需要在 v1 之后补齐协议矩阵、控制面、订阅服务和多出口池。

---

## 2. 目标定义

### 2.1 功能目标

1. 客户端优先接入广州入口
2. 广州到新加坡复用现有 Kilo / WireGuard 链路
3. 新加坡作为统一对外出口
4. 支持主流代理协议族，而不只限于 TCP relay
5. 支持 `Shadowrocket`、`ClashX`、`Mihomo/Clash`、`sing-box`、浏览器/系统代理等常见客户端
6. 提供统一订阅分发与多客户端模板渲染
7. 支持后续增加更多入口、出口、出口池和地域

### 2.2 非功能目标

1. 入口/出口角色清晰
2. Kilo 只负责传输平面，不承担业务代理语义
3. 数据面尽量短，公网监听组件采用 `hostNetwork`
4. 配置变更可审计、可灰度、可回滚
5. 至少具备连接数、失败率、延迟、带宽、协议分布、用户维度审计能力

### 2.3 非目标

1. 不把整个广州节点默认路由切到新加坡
2. 不把 Kilo 当成“自动代理产品”
3. 不承诺兼容所有冷门闭源私有协议
4. 不在 v1 中优先实现客户端透明代理 / 全局 TUN 接管

---

## 3. 对标成熟服务时，平台必须补齐什么

类似成熟中转服务的核心能力，不是“多开几个端口”，而是同时具备：

- 多协议入口
- 统一账号与认证
- 统一订阅输出
- 广州入口到新加坡出口的稳定中继
- UDP/QUIC 能力
- 线路池与健康摘除
- 用户维度审计、限速、配额、封禁
- 发布与回滚机制
- 观测与告警

因此，本方案采用 **配置源 + 数据面 + 订阅分发面** 的三层设计。

## 4. 总体架构

```text
                           ┌──────────────────────────────┐
                           │ edge-config-source           │
                           │ - Local YAML / Secret        │
                           │ - Config Render              │
                           │ - Subscription Render        │
                           └──────────────────────────────┘

Client
  |
  |  HTTP / SOCKS5 / SS / VLESS / Trojan / Hysteria2 / TUIC / WG
  v
[ Guangzhou Public Entry ]
  |
  v
[ edge-ingress-gateway DaemonSet ]
  - hostNetwork
  - 多协议监听
  - 用户认证
  - 接入日志
  - 上游出口选择
  |
  |  Kilo / WireGuard / L3 encrypted path
  v
[ edge-egress-gateway DaemonSet ]
  - hostNetwork
  - 仅接受来自广州入口 / Kilo 网段
  - 出站连接建立
  - UDP/QUIC/TCP 出口
  - 出口指标与审计
  |
  v
[ Singapore Public Egress ]
  |
  v
Destination
```

## 5. 架构决策

### 5.1 采用的总体形态

- **Kilo 作为跨地域传输平面**
- **广州入口部署 hostNetwork 的多协议 ingress gateway**
- **新加坡出口部署 hostNetwork 的 egress gateway**
- **配置源与数据面分离**
- **订阅分发独立于协议引擎**
- **入口与出口均通过 DaemonSet 编排**

### 5.2 为什么不再停留在“TCP relay”

只有 `TCP/L4 relay` 不足以支撑成熟代理平台，原因是：

- 无法覆盖 `SOCKS5 UDP ASSOCIATE`
- 无法覆盖 `Hysteria2`、`TUIC`、`WireGuard` 这类以 `UDP/QUIC` 为主的数据面
- 无法统一管理多协议认证与用户维度策略
- 无法为 `ClashX/Shadowrocket` 输出成体系的订阅配置

此外，不建议把“多跳中转”建立在客户端侧 `relay` 拼链能力上。客户端更适合消费统一订阅，真正的中转链路应由服务端网关平台控制。

### 5.3 v1 的现实选择

在现有双节点条件下，v1 推荐做成：

- **北向多协议入口**
- **南向统一新加坡出口**
- **协议能力以主流协议族为边界**
- **配置源先做最小可用**

---

## 6. 推荐技术栈

### 6.1 数据面

推荐以 **`sing-box` 作为主数据面引擎**，原因是：

- 单一引擎即可覆盖 HTTP、SOCKS、Shadowsocks、Trojan、VLESS、Hysteria2、TUIC、WireGuard、TUN 等主流能力
- 更适合做统一模板渲染与版本锁定
- 便于在 `hostNetwork` DaemonSet 中以节点级网关运行

要求：

- 必须锁定版本，不直接追 latest
- 配置必须由渲染器统一生成，不手工散落在节点上

### 6.2 客户端生态

- `Shadowrocket`：消费 `Shadowsocks`、`Trojan`、`VLESS`、`Hysteria2`、`TUIC`、`WireGuard`、`HTTP/SOCKS`
- `ClashX / Mihomo`：消费 `Mihomo/Clash` 订阅模板
- `sing-box`：消费 `sing-box` JSON / profile 模板
- 浏览器或系统代理：消费 `HTTP CONNECT` / `SOCKS5`

### 6.3 配置源

当前自用版不引入独立数据库或后台服务，而是使用：

- 本地 YAML 作为 source-of-truth
- 渲染脚本生成运行配置与订阅
- 运行态通过 Kubernetes `Secret/ConfigMap` 下发

未来如用户规模扩大，再评估独立后台服务。

## 7. 协议支持策略

## 7.1 v1 必须支持

- `HTTP CONNECT`
- `SOCKS5`
- `Shadowsocks`
- `Trojan`
- `VLESS`
- `Hysteria2`
- `TUIC`
- `WireGuard` 客户端接入
- `Mihomo/Clash` 订阅输出
- `sing-box` 订阅输出

## 7.2 v1 可选支持

- `VMess`
- WebSocket / gRPC / Reality 等特定封装
- DNS 出口代理

## 7.3 v2 再考虑

- 透明代理
- `TUN` 网关模式
- 基于策略的出口池调度
- 多新加坡出口池
- 多广州入口节点

> 说明：成熟商业中转服务通常并不依赖“一个端口兼容所有协议”，而是用统一控制面管理多个协议入口和多个客户端模板。

## 8. 数据面分层

### 8.1 北向入口层（广州）

职责：

- 监听公网协议端口
- 做认证与接入控制
- 记录接入日志
- 按用户、协议、策略选择新加坡出口
- 通过 Kilo 地址把流量转给新加坡 egress

要求：

- `hostNetwork: true`
- 仅落在 `edge.role=ingress`
- 显式声明端口
- readiness / liveness / startup probe

### 8.2 跨地域中继层（Kilo）

职责：

- 只做广州到新加坡的数据承载
- 提供 Kilo 私网地址与 WireGuard 加密链路

不负责：

- 客户端认证
- 出口池策略
- 订阅生成
- 用户审计

### 8.3 出口层（新加坡）

职责：

- 接收来自广州 ingress 的流量
- 建立最终外连
- 提供 TCP / UDP / QUIC 出口能力
- 上报出站成功率、连接时延、失败原因

要求：

- 监听端口不对公网开放给任意来源
- 仅允许广州入口节点公网 IP 或 Kilo 网段访问
- `hostNetwork: true`
- 仅落在 `edge.role=egress`

## 9. 配置源与订阅设计

## 9.1 组件

- `edge-config-renderer`
  - 生成 ingress/egress 的运行配置
- `edge-subscription-renderer`
  - 输出 `Mihomo/Clash`、`sing-box`、通用节点列表
- `edge-subscription-server`
  - 提供静态 HTTP 订阅文件
- `edge-health-controller`
  - 汇总出口健康状态，驱动摘除和恢复

## 9.2 配置来源

- Git 中保存：
  - 节点角色
  - 基础端口规划
  - 镜像版本
  - 协议开关
- 本地私密 YAML / Secret 存储：
  - 用户凭据
  - 订阅签名密钥
  - TLS 私钥
  - WireGuard 客户端密钥材料

## 9.3 订阅输出

同一份配置源元数据，渲染为：

- `Mihomo/Clash` YAML
- `sing-box` JSON
- `Shadowrocket` 可导入节点或订阅
- 通用 `HTTP/SOCKS` 连接信息

## 11. 端口规划原则

### 11.1 当前明确不能占用

- `80/443`：已由 `ingress-nginx` 占用
- `51820/udp`：Kilo / WireGuard 已占用

### 11.2 端口规划原则

- 公网入口端口由 `edge-ingress-gateway` 统一承接
- 新加坡出口监听端口只对广州入口或 Kilo 网段开放
- 不再使用 `NodePort` 作为代理数据面主路径
- 每种协议使用明确端口，不依赖“一个端口兼容全部协议”

### 11.3 v1 推荐做法

- `HTTP/SOCKS`：单独端口
- `Shadowsocks/Trojan/VLESS`：按协议族分端口
- `Hysteria2/TUIC/WireGuard`：按 UDP/QUIC 独立端口

## 12. Phase 1 实施收敛

为了尽快把“广州入口 / 新加坡出口”做成真实可验证的服务，本期先收敛为：

- `gz`：
  - 使用 `GOST` 做节点级 TCP/UDP 端口转发
  - 不在广州终止代理协议
  - 只负责公网监听与转发到 `sg` 的 Kilo IP
- `sg`：
  - 使用 `sing-box` 终止代理协议并直接出公网
  - 所有代理协议仅绑定 `sg` 的 Kilo IP，不直接绑定 `sg` 公网网卡
- `subscription`：
  - 使用轻量静态 HTTP 服务提供订阅文件
  - 订阅文件从本地 YAML 渲染生成
- 本期真实交付协议：
  - `HTTP CONNECT`
  - `SOCKS5`
  - `Shadowsocks`

这样做的原因：

- `GOST` 天然适合做多端口 TCP/UDP 转发
- `sing-box` 适合集中承接现代代理协议
- 静态订阅已经足够支撑客户端一键更新
- 先把 TCP 与 UDP 都跑通，比一次性把 TLS/QUIC/UI/数据库全塞进第一版更稳

实施资产与运维文档：

- `infra/platform/edge-gateway/README.md`

### 12.1 本期暂不落地

- `Trojan`
- `VLESS`
- `Hysteria2`
- `TUIC`
- `WireGuard` 客户端接入
- 用户配额与封禁控制面

这些能力仍保留在总设计里，但不作为第一轮上线阻塞项。

### 12.2 本期遗漏项补充

在原始草案基础上，需要补齐这些工程项：

- 明确 **证书策略**
  - TLS 类协议上线前，先决定 `ACME`、`DNS-01`、自签测试证书或 `Reality` 路径
- 明确 **入口 ACL**
  - 广州入口端口默认对公网开放；如需收敛来源，需要云安全组与平台 ACL 配合
- 明确 **出口绑定地址**
  - 新加坡代理协议服务只绑定 `10.4.0.2`
- 明确 **Kilo IP 漂移处理**
  - 若节点重建或 Kilo IP 变化，需同步更新入口转发配置
- 明确 **凭据轮换**
  - 用户密码与 Shadowsocks 密钥通过 Kubernetes Secret 管理，并提供轮换 SOP
- 明确 **订阅更新路径**
  - 订阅文件由静态 HTTP 服务提供
  - 客户端使用固定 URL 定期更新
- 明确 **验证标准**
  - 至少验证 HTTP、SOCKS5、Shadowsocks 三条链路的实际出口 IP 为 `sg`

## 13. 安全模型

### 12.1 用户认证

- 用户名/密码
- 协议密钥
- UUID / token
- WireGuard peer 密钥

### 12.2 平台安全

- 数据面配置由配置源与渲染脚本统一下发
- Secret 不入库
- 入口与出口节点最小开放面
- 出口默认按用户、协议、来源做限速与限额

### 12.3 审计

至少记录：

- 用户
- 协议
- 入口节点
- 出口节点
- 源地址
- 目的地址或归类标签
- 会话开始/结束时间
- 上下行字节数
- 失败原因

---

## 14. 观测要求

### 13.1 必备指标

- 活跃连接数
- 新建连接速率
- 协议分布
- 每用户连接数 / 吞吐
- 出口成功率
- TCP 建连时延
- UDP 会话成功率
- Kilo RTT / WireGuard handshake / 带宽
- ingress/egress 进程重启次数

### 13.2 日志

- 接入日志
- 鉴权失败日志
- 出口失败日志
- 配置下发和热重载日志
- 用户配额触发日志

### 13.3 告警

- 全部出口不可用
- 某协议入口全部失败
- WireGuard handshake stale
- 单用户连接数异常
- 进程频繁重启
- 配置下发失败

## 15. 分阶段实施

## Phase 0：基线与标签

目标：

- 为现有两节点补齐 `edge.role` / `edge.location`
- 建立 `edge-system` namespace
- 确认端口规划与安全组

交付：

- 节点标签
- namespace
- 端口规划表

## Phase 1：最小可用配置源与订阅

目标：

- 建立本地 YAML 配置源
- 建立配置渲染与静态订阅服务
- 先不做复杂 UI，优先 Git + Secret/ConfigMap 管理

交付：

- `edge-config-renderer`
- `edge-subscription-renderer`
- `edge-subscription-server`

## Phase 2：广州入口 / 新加坡出口

目标：

- 上线 `edge-ingress-gateway`
- 上线 `edge-egress-gateway`
- 打通广州入口到新加坡出口

交付：

- 多协议入口
- 新加坡统一出口
- 端到端连通性验证

## Phase 3：UDP/QUIC 与客户端模板

目标：

- 打通 `Hysteria2` / `TUIC` / `WireGuard`
- 输出 `Mihomo/Clash`、`sing-box`、`Shadowrocket` 模板

交付：

- UDP/QUIC 能力
- 多客户端订阅

## Phase 4：商业化能力补齐

目标：

- 用户、限速、配额、封禁
- 多出口池
- 健康摘除与恢复
- 滚动升级与灰度

交付：

- 统一账号体系
- 出口池调度
- 运维 SOP

## 16. 当前双节点下是否能直接实施

可以直接开始，但只能按以下顺序落地：

1. 先做标签、namespace、端口规划
2. 先落地新加坡 egress
3. 再落地广州 ingress
4. 最后补配置源和订阅分发

当前 **不能直接宣称“对标成熟商业代理平台已完成”**，因为还缺：

- 多入口 / 多出口高可用
- 用户系统
- 统一认证与配额
- 订阅服务
- UDP/QUIC 能力
- 协议版本管理与灰度

---

## 17. 最终结论

最终推荐方案是：

- **Kilo 只做跨地域传输平面**
- **广州做 hostNetwork 的多协议入口网关**
- **新加坡做 hostNetwork 的统一出口网关**
- **配置源与订阅分发独立**
- **v1 覆盖主流代理协议族，而不是只做 TCP relay**
- **后续通过多出口池、多入口节点和用户体系继续演进**

这套方案与现有双节点集群兼容，能够从当前基线逐步演进到接近成熟中转服务的工程形态。
