### 5.x.6 修复：镜像拉取与 CRD（2026-03-01）

#### 5.x.6.1 配置 k3s registry mirror（gz，将 `docker.io` mirror 到可达的 `registry.rancher.com`）

```bash
sudo mkdir -p /etc/rancher/k3s

mirrors:
  docker.io:
    endpoint:
      - "https://registry.rancher.com"
EOF
sudo systemctl restart k3s
```

#### 5.x.6.2 离线导入 `docker.io/squat/kilo:0.6.0`（sg 拉取 -> gz 导入 containerd）

原因：

- `registry.rancher.com` 不包含 `squat/kilo`
- Kilo 上游 manifest 的 initContainer 曾显式设置 `imagePullPolicy: Always`，即使本机已有镜像也会强制拉取；本仓库已将 `infra/k3s/manifests/kilo-k3s.yaml` 调整为 `IfNotPresent`

在 sg：

```bash

sudo skopeo copy docker://squat/kilo:0.6.0 docker-archive:/tmp/squat-kilo_0.6.0.tar:squat/kilo:0.6.0
```

将 tar 文件传到 gz（中转可用你的操作机），并在 gz 导入：

```bash
sudo k3s ctr images import /home/ubuntu/squat-kilo_0.6.0.tar
sudo k3s ctr images ls | grep -i kilo
```

### 5.x.8 安装 ingress-nginx（Helm，离线 chart + 离线镜像，2026-03-01）

阻塞背景：

- gz 无法访问 `registry.k8s.io` 的实际后端（`*.docker.pkg.dev`），导致 admission hook Job `ImagePullBackOff`
- gz 无法稳定访问 ingress-nginx chart 的 GitHub Releases 下载地址，`helm upgrade` 拉取 chart 超时

#### 5.x.8.1 在 sg 准备 chart 与镜像（可出网机器）

下载固定版本 chart（4.14.3）：

```bash
curl -fL -o /tmp/ingress-nginx-4.14.3.tgz \
  https://github.com/kubernetes/ingress-nginx/releases/download/helm-chart-4.14.3/ingress-nginx-4.14.3.tgz
ls -lh /tmp/ingress-nginx-4.14.3.tgz
```

导出镜像为 tar（用于导入 gz 的 containerd）：

```bash
sudo apt-get install -y skopeo

sudo skopeo copy \
  docker://registry.k8s.io/ingress-nginx/controller:v1.14.3 \
  docker-archive:/tmp/ingress-nginx-controller_1.14.3.tar:registry.k8s.io/ingress-nginx/controller:v1.14.3

sudo skopeo copy \
  docker://registry.k8s.io/ingress-nginx/kube-webhook-certgen:v1.6.7 \
  docker-archive:/tmp/ingress-nginx-kube-webhook-certgen_1.6.7.tar:registry.k8s.io/ingress-nginx/kube-webhook-certgen:v1.6.7
```

#### 5.x.8.2 传到 gz 并导入 containerd

将 chart 与 tar 传到 gz（中转可用你的操作机）：

```bash
# chart
scp /tmp/ingress-nginx-4.14.3.tgz gz.butcoder.com:/home/ubuntu/ingress-nginx-4.14.3.tgz

# images
scp /tmp/ingress-nginx-controller_1.14.3.tar gz.butcoder.com:/home/ubuntu/ingress-nginx-controller_1.14.3.tar
scp /tmp/ingress-nginx-kube-webhook-certgen_1.6.7.tar gz.butcoder.com:/home/ubuntu/certgen.tar
```

在 gz 导入镜像：

```bash
sudo k3s ctr images import /home/ubuntu/ingress-nginx-controller_1.14.3.tar
sudo k3s ctr images import /home/ubuntu/certgen.tar
sudo k3s ctr -n k8s.io images ls | grep -E 'ingress-nginx/(controller|kube-webhook-certgen)' || true
```

> 备注：ingress-nginx chart 里镜像默认带 `@sha256:<digest>` 固定。由于上面导入的是 `linux/amd64` 的单平台 manifest，
> `ctr images ls` 显示的 digest 与 chart 使用的 manifest-list digest 不一致。
> 为避免 kubelet 继续触发远程 pull，这里给 containerd 增加了 digest-only 的 tag（本质是额外 alias）。

在 gz 为镜像增加 digest-only tag（以 chart 使用的 digest 为准）：

```bash
sudo k3s ctr -n k8s.io images tag registry.k8s.io/ingress-nginx/controller:v1.14.3 \
  registry.k8s.io/ingress-nginx/controller@sha256:82917be97c0939f6ada1717bb39aa7e66c229d6cfb10dcfc8f1bd42f9efe0f81

sudo k3s ctr -n k8s.io images tag registry.k8s.io/ingress-nginx/kube-webhook-certgen:v1.6.7 \
  registry.k8s.io/ingress-nginx/kube-webhook-certgen@sha256:7c74a715af2c94cb734785b4d3ea1357b4f02b88e1e123c622a9cb68b62f669c
```

> 说明：实际 admission hook Pod 的 image 字段形如 `...:v1.6.7@sha256:<digest>`，但 containerd 在解析时会使用 digest-only 形式访问远端，
> 所以上述 digest-only tag 是关键点（避免触发远端 pull）。

### 5.x.12 修复：跨地域 apiserver Endpoints 使用 gz 公网（2026-03-01）

背景：跨地域时 `gz`/`sg` 私网不可互通；若集群内 `kubernetes.default` 的 Endpoints 指向 `gz` 私网（如 `10.0.8.11:6443`），会导致 `sg` 上的 CNI/Kilo 在启动阶段无法访问 apiserver（形成启动闭环）。

在 `gz` 写入配置（注意：**不要**设置 `node-ip` 为公网 IP；公网 IP 不在网卡上会导致 kubelet TLS SAN 不匹配，`kubectl logs/exec` 失败）：

```bash
sudo mkdir -p /etc/rancher/k3s
cat <<'EOF' | sudo tee /etc/rancher/k3s/config.yaml >/dev/null
advertise-address: 106.55.163.135
node-external-ip: 106.55.163.135
EOF

sudo systemctl restart k3s
sudo k3s kubectl -n default get endpoints kubernetes -o jsonpath='{.subsets[*].addresses[*].ip}{"\n"}'
```

输出摘要：

- `kubernetes` Endpoints：`106.55.163.135`

### 5.x.13 修复：Kilo endpoint 选择（force-endpoint，2026-03-01）

现象：Kilo 可能会自动把 `kilo.squat.ai/endpoint` 设置为节点私网（跨地域不可达），导致 WireGuard peer 无法握手。

在操作机执行（把 nodeName 替换为真实）：

```bash
kubectl annotate node vm-8-11-ubuntu kilo.squat.ai/force-endpoint="106.55.163.135:51820" --overwrite
kubectl annotate node vm-0-11-ubuntu kilo.squat.ai/force-endpoint="43.156.60.56:51820" --overwrite

# 触发重建（可选）
kubectl -n kube-system delete pod -l app.kubernetes.io/name=kilo
```

验证（摘要）：

- `kubectl get nodes` 注解中：
  - `kilo.squat.ai/endpoint` 与 `kilo.squat.ai/force-endpoint` 均为公网 `:51820`
- `wg show`：两端 peer 均有 `latest handshake` 且有收发流量

### 5.x.15 修复：Pod 无法跨节点访问（gz 的 iptables FORWARD=DROP，2026-03-01）

现象：在节点上 `curl` 对端 PodIP/ClusterIP 可通，但在 Pod 内 `curl` 超时。

定位（gz）：

```bash
sudo iptables -S FORWARD | head -n 1
```

输出摘要：

- 初始为 `-P FORWARD DROP`

临时修复（gz）：

```bash
sudo iptables -P FORWARD ACCEPT
```

持久化（gz）：创建并启用 systemd one-shot（同时绑定到 `docker.service`，避免 Docker 重置策略）：

```bash
cat <<'EOF' | sudo tee /etc/systemd/system/iptables-forward-accept.service >/dev/null
[Unit]
Description=Ensure iptables FORWARD policy is ACCEPT
After=network-online.target docker.service
Wants=network-online.target
PartOf=docker.service

[Service]
Type=oneshot
ExecStart=/usr/sbin/iptables -w -P FORWARD ACCEPT
ExecStart=/usr/sbin/ip6tables -w -P FORWARD ACCEPT
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
WantedBy=docker.service
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now iptables-forward-accept.service
sudo systemctl status iptables-forward-accept.service --no-pager -l | sed -n '1,12p'
```
