# 07-公网访问与统一认证链路

目标：把当前公网 Web 服务的默认接入方式固定下来，避免后续每新增一个公网访问服务都重新设计入口和认证链路。

当前结论：

- 公网 Web 入口统一走 `Traefik + Gateway API`
- 公共认证链路统一走 `Authelia`
- 当前默认认证级别为 `one_factor`
- 当前默认入口形式为 `公网 IP + 路径前缀`
- 当前公共入口首页是自定义 landing `/`
- 当前认证后的默认门户是 `/home/`
- 当前 `Grafana` 已经作为第一条完整样例落地

## 当前实际链路

```text
client
  -> Traefik (80/443, public-gateway)
  -> Traefik Middleware ForwardAuth
  -> Authelia (/auth/)
  -> back to Traefik
  -> target service
```

当前门户和认证之间的关系是：

```text
client
  -> https://106.55.163.135/
  -> public landing
  -> public-portal Service
  -> if authenticated -> redirect /home/
  -> login button -> https://106.55.163.135/auth/?rd=https://106.55.163.135/home/

client
  -> https://106.55.163.135/home/
  -> HTTPRoute public-portal (/home)
  -> Middleware portal-authelia-forwardauth
  -> authenticated portal
```

当前 `Grafana` 的具体链路是：

```text
client
  -> https://106.55.163.135/grafana/
  -> HTTPRoute monitoring-grafana
  -> Middleware monitoring-grafana-authelia-forwardauth
  -> Authelia forward-auth
  -> monitoring-grafana Service
  -> Grafana auth.proxy trusted headers
```

## 当前组件分工

### Traefik

- 负责公网 `80/443`
- 负责 `Gateway` / `HTTPRoute`
- 负责把认证前置中间件挂到具体路由

相关资产：

- `infra/platform/traefik/values.yaml`
- `infra/platform/traefik/public-gateway.yaml`
- `infra/platform/traefik/http-redirect.yaml`

### Authelia

- 负责统一登录入口
- 负责前置认证判断
- 负责用户库、会话、TOTP/WebAuthn 运行态

当前实现：

- 文件用户库
- SQLite 本地存储
- QQ SMTP 通知
- `default_policy = one_factor`
- 默认登录成功回跳到门户 `/`

相关资产：

- `infra/platform/authelia/values.yaml`
- `infra/.secrets/authelia-users-database.yml`

### Portal

- 负责承接公网访问的 landing 和认证后的门户
- 当前只维护一个公开入口卡片：`Grafana`
- 当前仍然使用公网 IP，不依赖 DNS
- `/` 公开，只保留统一登录入口
- `/home/` 受 `Authelia ForwardAuth` 保护，认证后才展示具体服务卡片
- 已登录用户再次访问 `/` 时，由 landing 页自动跳到 `/home/`

相关资产：

- `infra/platform/portal/portal-configmap.yaml`
- `infra/platform/portal/portal-deployment.yaml`
- `infra/platform/portal/portal-service.yaml`
- `infra/platform/portal/portal-forwardauth-middleware.yaml`
- `infra/platform/portal/portal-httproute.yaml`
- `infra/platform/portal/portal-networkpolicy.yaml`

### Grafana

- 不再直接对接 OIDC
- 改为 `auth.proxy`
- 信任来自 Traefik + Authelia 的用户头

相关资产：

- `infra/platform/monitoring/victoria-metrics-k8s-stack/values.yaml`
- `infra/platform/monitoring/grafana/grafana-httproute.yaml`
- `infra/platform/monitoring/grafana/grafana-forwardauth-middleware.yaml`
- `infra/platform/monitoring/grafana/grafana-networkpolicy.yaml`

## 当前默认接入模式

后续新增“走公网链路访问”的内部 Web 服务，默认按下面顺序评估：

1. 先挂到 `Traefik public-gateway`
2. 默认接 `Authelia ForwardAuth`
3. 如果后端支持 trusted header / auth proxy，则复用这一条统一认证链路
4. 如果后端本身仍需要自带登录，再单独评估是否保留应用自身登录

当前默认模式不是：

- 每个服务单独暴露公网端口
- 每个服务单独做 OIDC
- 每个服务单独维护自己的公网登录入口
- 登录完成后停留在 `Authelia` 默认 `authenticated` 页面
- 匿名访问就能看到真实内部系统门户

## 推荐接入模板

### 模式 A：前置认证 + 后端 trusted headers

适用：

- Grafana 这种支持 `auth.proxy` 的系统
- 需要“退出 Authelia 后立即失效”的系统

需要做的事：

1. 建一个 `Traefik Middleware`，指向 `Authelia forward-auth`
2. 在目标 `HTTPRoute` 上挂这个中间件
3. 后端启用 trusted header / auth proxy
4. 用 `NetworkPolicy` 限制只有 `traefik` namespace 能访问后端 Pod

优点：

- 登录和退出体验统一
- 不依赖应用自己的 OIDC logout 能力
- 公共认证链路清晰

### 模式 B：前置认证 + 应用自带登录

适用：

- 不支持 trusted header 的系统
- 只想把公网入口先挡在统一认证后面

特点：

- `Authelia` 负责前门
- 应用内部仍可能保留自己的本地登录
- 安全性和体验都弱于模式 A

### 模式 C：应用直接走 OIDC

当前不作为默认方案。

原因：

- 退出体验不如前置认证稳定
- 每个应用都要单独做 OIDC client 管理
- 当前规模下收益不明显

后续如果某个应用必须原生 OIDC，再单独评估。

## 当前安全边界

### 入口边界

- 只有 `Traefik` 对公网开放 `80/443`
- 应用不直接绑定宿主机公网端口
- 公开 landing 允许匿名访问，但只承载导航和 SSO 入口
- 真实门户 `/home/` 仍然受 `Authelia` 保护

### 认证边界

- `Authelia` 统一承接 `/auth/`
- 当前默认 `one_factor`
- 当前未把所有公网服务都强制提升到 `two_factor`

### 后端信任边界

凡是使用 trusted headers 的后端，必须同时满足：

- 只有 `Traefik` 可以访问后端 Pod
- 后端不直接对公网暴露
- 后端不信任来自其他 Pod 的伪造头

`Grafana` 当前已经通过 `NetworkPolicy` 落地这一点。

## 当前限制

### WebAuthn

当前公网入口仍是 IP：

- `https://106.55.163.135/...`

因此：

- WebAuthn/Passkey 不稳定
- 当前不要把它当成主认证路径
- 先用密码 / TOTP
- 等后续有正式 DNS 再回头启用 WebAuthn

### 公网地址形式

当前还是路径前缀模式：

- `/`
- `/auth/`
- `/grafana/`

后续若引入更多服务，路径前缀数量会继续增加；有 DNS 后更适合切子域名。

## 运维检查

### 入口检查

```bash
kubectl get gatewayclass,gateway,httproute -A
kubectl -n traefik get deploy,pod,svc
curl -kI https://106.55.163.135/auth/
curl -kI https://106.55.163.135/
curl -kI https://106.55.163.135/home/
curl -kI https://106.55.163.135/grafana/
```

### 认证链路检查

```bash
kubectl -n authelia get deploy,pod,svc,httproute
kubectl -n authelia logs deploy/authelia --since=10m
```

### 服务接入检查

```bash
kubectl -n monitoring get middleware,httproute,networkpolicy | rg grafana
kubectl -n portal get deploy,pod,svc,httproute,networkpolicy,middleware
kubectl -n monitoring get cm monitoring-grafana -o jsonpath='{.data.grafana\.ini}'
```

## 后续新增公网服务时的默认动作

以后新增一个“需要从公网访问”的内部服务，默认先问自己这 4 个问题：

1. 是否应该统一挂到 `Traefik public-gateway`？
2. 是否应该先接 `Authelia ForwardAuth`？
3. 后端是否支持 trusted header / auth proxy？
4. 是否需要补 `NetworkPolicy`，确保只有 `Traefik` 能访问？

如果答案分别是：

- 是
- 是
- 是
- 是

那就直接复用当前公共认证链路，不再单独设计新的公网登录方案。
