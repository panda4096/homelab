# 06-备份恢复与审计

## 备份范围

三类资产必须被备份覆盖：

1. **共享 PostgreSQL 实例**（`infra/data/postgresql`，namespace `data`）
   包含三个业务 database：`firefly`、`ghostfolio`、`finbrain`。一次 `pg_dumpall` 即可覆盖三家。
2. **finbrain 上传目录**（`FINBRAIN_UPLOADS_DIR` = `/var/finbrain/uploads`）
   HSBC PDF、截图、Futu CSV 等原始凭证二进制文件。PVC `finbrain-uploads`，`local-path`，和 finbrain pod 绑定到同一节点（`region=gz`）。
3. **Ghostfolio Redis** 不需要长期备份，缓存可重建。

## finbrain 重点

`finbrain` 的审计价值最高，因为它持有：

- `raw_payload`（结构化摘要）
- `raw_doc_uri` 指向的原始上传文件（和 Postgres 是绑定关系，恢复时必须两个都在）
- review 决策
- `(source, source_ref)` 去重记录
- `wealth_products` 及其 `wealth_product_code` 关联

恢复时若只恢复了 Postgres 而丢失了上传目录，`raw_doc_uri` 会变成悬空引用，审计能力会丢失。

## 当前已知限制（重要）

**本次 update 没有真正的备份实现**。现状：

- 仓库里的 `infra/apps/finbrain/finbrain-db-backup-cronjob.yaml` 被标记为 `suspend: true`，不会每日运行
- 它原本引用的外部 S3（`ap-east-1`）字段 `AWS_ACCESS_KEY_ID` / `S3_BUCKET` 等是早期 agent 生成的占位，**从未真正配置过**
- `finbrain-uploads` PVC 也没有跨节点备份，只受单节点 local-path 保护
- 共享 PostgreSQL 本身同样在 `region=gz` 单节点，没有副本

这意味着 Phase 1 上线之前**必须**单独一单专门决策并落地可用的备份方案。决策选项：

- **两节点内部同步**：把 pg dump 和 uploads 目录 rsync 到 `region=sg` 另一个节点的本地卷。好处：不依赖外部服务；坏处：需要两个节点同时失效才算真事故，但 rsync 的 orchestration 要写。
- **外部对象存储**：配置真实 S3 兼容 endpoint（阿里云 OSS / 腾讯云 COS / Cloudflare R2），沿用已有 CronJob 模板。好处：off-site；坏处：依赖外部可用性，要付钱。

在上述决策落地之前，**不要把真实资金数据写入 finbrain**。Phase 1 开始导入信用卡账单之前，新开一单名为 `data-layer-backup` 的变更，把 CronJob 重写。

## 目标策略（待落地）

一旦备份方案决定：

- 每日加密 `pg_dump` 覆盖 `data/postgresql` 的全部三个 database
- 每日增量同步 `finbrain-uploads` PVC 的内容（只做增量，因为原件不变）
- 保留：
  - 日备 7 天
  - 周备 4 周
  - 月备 12 个月
- 每季度做一次恢复演练

## 恢复原则

- Firefly / Ghostfolio 用各自 database 恢复业务状态
- finbrain 必须同时恢复 database（pg 中的行）和 `finbrain-uploads` PVC（原始文件），两者任一缺失都无法恢复审计能力
- dashboard 恢复后应以底层系统重新聚合，不保留独立状态

## 审计要求

- 所有导入必须写入审计日志
- 去重命中必须可见
- dispatcher 失败必须保留原始 payload 和失败原因
- 每条理财活动的 `wealth_product_code` 在 review 队列里可见，缺失时提示人工补齐
